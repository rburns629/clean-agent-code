# Rules results: 2026-10-31

Tests the working-style section of `AGENTS.md` and the project-maturity guidance
added in commit `51dbc02`, which the
[same-day slop run](2026-10-31-slop.md) could not exercise. Run with a scripted
multi-turn harness in `evaluations/harness/rules/` on the slop codebases, in
isolated Docker containers.

## Summary

- **Maturity changes test depth in the expected direction.** With full
  clean-agent-code, a context recording a production service produced three to five
  times the tests of one recording a prototype. Prototypes still passed every hidden
  validation test.
- **Blocked work is held and reported.** Asked to "clean up" a package, every control
  run deleted an unused module; every full run finished the other requests, left the
  module, and asked for approval with a specific proposal and recovery command.
- **Mistakes get a cause and proposed wording.** Every full run stated what went
  wrong and proposed a `PROJECT_CONTEXT.md` line without editing it. No context-only
  run did either.
- **A correction to queued work showed no difference.** Both conditions planned
  first, applied the correction, and finished the appended item.
- **The backup procedure blocked two of three full fixes; a new exemption fixed it.**
  Revising files edited in the previous turn made two full runs stop to ask for a
  backup location. After `standards/SECURITY.md` let an agent's own task edits use the
  starting commit as their recovery copy, a re-run applied the fix in all three.

For comparison, full runs without a maturity row in the
[slop run](2026-10-31-slop.md) added about 24 test lines on T1 and 12 on T4, so the
production row raised depth more than the prototype row lowered it. No run in any
scenario apologized.

In X, the two blocked full runs had a tested fix ready, one as a patch and one in a
scratch copy. They cited the backup procedure in `standards/SECURITY.md`: their own
uncommitted edits from the first turn no longer matched the commit, so the
clean-tracked-file exemption did not apply and no backup location was documented.
The re-run used fresh fixtures and the framework with the
[agent's own task edits](../../standards/SECURITY.md#the-agents-own-task-edits)
exemption; no full run stopped.

## Limitations

- Three replicates per pair; only the all-or-nothing differences are clear.
- Headless sessions cannot receive a message mid-turn, so scenario C tests a
  correction to planned work, not an interruption of work in progress.
- Keyword checks were confirmed by reading every final message, by the same session
  that wrote the rules; there was no blind review.
- Scenario Q tests one kind of block, an ambiguous destructive request. Whether
  control's deletion was wrong depends on the user; the rule makes it a question.
